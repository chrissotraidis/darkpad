# Graphics substrate audit — Phase 0.5

Evidence pass for charter §Phase 0.5. Pin `bfea0618`
(`UPSTREAM_PIN`); every line reference is against that pin.
No build was run for this document; everything here is read from source.

Candidates: **(a)** ANGLE-Metal feeding an ES 3.0 context to the existing
`vendor/dabs-mod/port/fast3d/gfx_opengl.cpp`; **(b)** a native Metal
backend implementing `struct GfxRenderingAPI`
(`vendor/dabs-mod/port/fast3d/gfx_rendering_api.h:18-71`, 44 entry points).

---

## 0. What the seam looks like today

`port/src/video.c:79-80` sets `wmAPI = &gfx_sdl; renderingAPI = &gfx_opengl_api;`
— two assignments. That is the whole backend switch, and it is already the
build-time seam the charter asks for. `gfx_pc.cpp` never names a backend.

Context creation is `gfx_sdl2.cpp:148-197`: a fallback ladder of
`SDL_GL_SetAttribute` rows, row 4 being
`{ 3, 0, SDL_GL_CONTEXT_PROFILE_ES }` annotated *"es3: don't really support
ES properly, but we can try"*. `SDL_GL_SetSwapInterval(1)` at :206.
SDL **2** (`vendor/dabs-mod/CMakeLists.txt:255`), not SDL3 — the family's
ANGLE shims (dhewm3, realrtcw) are SDL3, so their glue needs a small port.

## 1. Option (a) — ANGLE-Metal into `gfx_opengl.cpp`

### 1.1 The bundled glad already has an ES profile

`port/fast3d/glad/glad.h:1-30` — generated by glad 0.1.36 with
`APIs: gl=4.1, gles2=3.0`. Both `gladLoadGLLoader` (glad.c:1512) and
`gladLoadGLES2Loader` (glad.c:1861) exist, and `find_coreGL` parses the
`"OpenGL ES "` version prefix (glad.c:1466-1468). Extensions compiled in
include `GL_EXT_texture_filter_anisotropic`, `GL_KHR_debug`,
`GL_APPLE_framebuffer_multisample`. `gfx_opengl_init` nonetheless calls only
the **desktop** loader (`gfx_opengl.cpp:1035`) — see patch P1.

### 1.2 GLSL emitted when `gl_es` is true — legal

`gfx_opengl.cpp:1077-1080` sets `gl_glsl_version = 300` and the version
string `"300 es"`, and every `>= 130` branch then takes the modern path:
`in`/`out` (`:258-264`, `:346-349`), `texture()` not `texture2D`
(`:349`), `out vec4 outColor` (`:452-454`). That is exactly right for
ESSL 3.00. Checked construct by construct, all legal under ESSL 3.00:

- `textureSize` (`:492`); integer ops `float(i & 3)`, `float(i >> 2)` in
  the blur (`:427`); `mix(vec4, vec4, int)` (`:432`, `:443` — ESSL 3.00
  §5.10 permits the implicit `int`→`float`); `lowp`/`mediump` qualifiers
  (`:421-436`); `fract`/`sin`/`dot`/`mod`/`step`/`sign`/`discard`/
  `gl_FragCoord` in `random()` (`:399-402`), `filter3point()`
  (`:405-413`), the dither (`:143`, `:586-590`), `WRAP` (`:358`) and
  `texEdge` (`:463-484`); the `0.3f` suffix (`:334`, ESSL 3.00 §4.1.4).
- **No `#extension` directive is emitted anywhere** (grepped: zero hits).

Two real defects, both one-liners:

- **`precision mediump float;` is emitted in the VERTEX shader**
  (`:254-256`). On Apple GPUs `mediump` is fp16, so `gl_Position` and the
  interpolated tex coords would be computed at half precision. ESSL 3.00
  defaults vertex float to `highp` — this line actively makes it worse.
- **Same line in the fragment shader** (`:342-344`). Fragment default is
  undefined-must-declare, so it cannot simply be deleted, but `highp` is
  what the XBLA path needs: `xblatex.c:35` allows records up to
  `XBLATEX_MAXDIM 4096`, and `0.5 / texSize` in `texEdge` (`:499-511`)
  at 4096 is 1.2e-4 — below fp16's useful resolution near 1.0. Expect
  edge smearing on large XBLA tiles at mediump.

### 1.3 GL entry points and enums under ES 3.0

Legal as written, ES 3.0 core: FBOs/renderbuffers, `GL_DEPTH24_STENCIL8`
(`:1381`, `:1424`), `GL_RGB8`/`GL_RGBA8` (`:1364`, `:1409`, `:770` —
both are color-renderable in ES 3.0), `glRenderbufferStorageMultisample`
(`:1414`), `glBlitFramebuffer` (`:1512`, `:1590`), `GL_MAX_SAMPLES`
(`:2197`), VAOs (`:1105-1106`), PBOs + `glMapBufferRange` (`:2043`,
`:2085`), `glPolygonOffset` (`:831-849`), `glReadBuffer(GL_BACK)`,
`GL_IMPLEMENTATION_COLOR_READ_FORMAT` (`:2019`).

Already ES-aware in upstream: `glDepthRangef` is preferred over
`glDepthRange` (`:862-867`); `GL_FRONT` is avoided under `gl_es`
(`:1585`); `GL_MIRROR_CLAMP_TO_EDGE` falls back to `GL_MIRRORED_REPEAT`
(`:1071-1074`); `GL_DEPTH_CLAMP` is gated on `GLAD_GL_ARB_depth_clamp`,
which `gfx_opengl_init_extensions` deliberately leaves 0 under ES
(`:1006`), so the `gl_Position.z *= 0.3` hack (`:332-335`) runs instead;
`glBindFragDataLocation`, `GL_R8`/`GL_RG8` targets and `GL_BGRA` reads
live only inside the two `gl_es`-gated passes (`:1210`, `:1793`).
**No `glPolygonMode`, `glDrawBuffer`, or `glGetTexImage` anywhere.**

Not present at all in the source: nothing desktop-only survives outside
those guards. The problems are the two below and the precision pair above.

### 1.4 Verdict list

**Works as is** — the whole shader generator (combiner, fog, grayscale,
text outline, three-point, blur, dither, stretched-edge clamp), the
framebuffer + MSAA + resolve + copy path, sampler state, PBO capture
plumbing, `GL_KHR_debug` (guarded, ANGLE supports it), anisotropy
(ANGLE-Metal exposes `EXT_texture_filter_anisotropic`; the enum values
`0x84FE`/`0x84FF` at glad.h:2726-2727 are shared with the ARB name the
code uses).

**Needs a patch** (overlay, per Ground rule 1):

| # | What | Where | Est. |
|---|------|-------|------|
| P1 | Call `gladLoadGLES2Loader` when the context is ES (read `SDL_GL_CONTEXT_PROFILE_MASK` before loading). Today the desktop loader resolves desktop-only names to NULL, one `LOG_ERROR` each via `gl_load_proc` (`:996`), and leaves `GLAD_GL_ES_VERSION_3_0` at 0. Mostly cosmetic — the ES 3.0 names are spelled identically — but the log noise would drown a real failure. | `:1035-1043` | ~20 |
| P2 | `highp` in the vertex shader (delete or raise the `mediump` line). | `:254-256` | 2 |
| P3 | `precision highp float;` in the fragment shader. | `:342-344` | 2 |
| P4 | `read_screen_pixels` asks for `GL_RGB` (`:1630`). **Illegal in ES 3.0** — only `GL_RGBA`/`GL_UNSIGNED_BYTE` plus the queried preferred pair are guaranteed. It fails cleanly (the `glGetError` check at `:1632` returns false), but that kills F12 **and `--screenshot-frame`, which is the Phase 0.4 regression vehicle**. Read RGBA into a scratch buffer and pack to RGB. | `:1618-1638` | ~30 |
| P5 | Guard the anisotropy calls on the extension flag instead of calling blind. Fine on ANGLE, `GL_INVALID_ENUM` elsewhere. | `:814`, `:2178` | ~8 |
| P6 | `resolve_msaa_color_buffer` blits a multisample source with src/dst rects that may differ (`:1512`) — `GL_INVALID_OPERATION` on ES3 *and* desktop. `gfx_pc.cpp:3989-4002` always matches the sizes today, so it is latent; add the guard while we are here. | `:1502-1516` | ~6 |
| P7 | Upstream bug, substrate-independent: `:1514` passes `current_framebuffer` (a **vector index**) where an FBO **name** is wanted; `:1592` does the same thing correctly. Carry the fix upstream. | `:1514` | 1 |

Total ≈ 70 lines of overlay patch. That is the honest cost of the
"don't really support ES properly" row.

**Feature loss on ES 3.0** (not fixable by an `#ifdef`):

- **Vivid Colours / Black Level does not run.** `gfx_opengl_grade_init`
  returns false on `gl_es` outright (`:1210`). The Phase 2 checklist
  names those two settings as "verified to render". Reimplementing the
  pass for ESSL 3.00 is not hard (drop `glBindFragDataLocation`, add the
  `#version 300 es` header) but it is ~60 new lines that must be written,
  and the same pass must be written from scratch for option (b) too.
- **NV12 GPU capture path is off** (`:1793`). Irrelevant — ffmpeg
  recording is already on the iOS deadlist.
- **`GL_MIRROR_CLAMP_TO_EDGE`** has no ES equivalent, so
  `G_TX_MIRROR|G_TX_CLAMP` tiles get `GL_MIRRORED_REPEAT`. Metal on iOS
  has the same hole (`mirrorClampToEdge` is macOS-only), so this is a
  wash between the options, not a discriminator.
- **`GL_DEPTH_CLAMP`** likewise absent on both; both substrates inherit
  the `z *= 0.3` hack and whatever depth-precision cost it carries.
- MSAA `2` silently becomes `4`: Metal offers no 2-sample target and
  ANGLE rounds up (q2repro `DECISIONS.md` D-VR-R20). Cosmetic menu lie.

### 1.5 How ANGLE gets its context (family pattern)

dhewm3 and realrtcw do **not** use SDL's GL path. They create EGL
directly: `SDL_Metal_CreateView` → `SDL_Metal_GetLayer` → cast to
`CAMetalLayer*`, `eglGetPlatformDisplayEXT(EGL_PLATFORM_ANGLE_ANGLE, {EGL_PLATFORM_ANGLE_TYPE_ANGLE,
EGL_PLATFORM_ANGLE_TYPE_METAL_ANGLE})`, then
`eglCreateWindowSurface` with **`EGLNativeWindowType` = the
`CAMetalLayer*`** — `~/dev/dhewm3-ios/app/ios/ios_angle.mm:66-137`
and `~/dev/realrtcw-ios/app/Sources/ios_egl.m:39-106`.
`libEGL`/`libGLESv2` ship as xcframeworks embedded in `Frameworks/`
(`~/dev/dhewm3-ios/scripts/make-angle-xcframeworks.sh:60-68`);
`OpenGLES.framework` must link **after** ANGLE or SDL's EAGL symbols win
(dhewm3 `DECISIONS.md:519-524`).

Prebuilt slices already exist on disk — ios device/sim and **visionOS**
device/sim — at `~/dev/realrtcw-ios/work/angle/out/`, ANGLE
`e25e8d8565f7` / 2.1.1, Metal-only, `angle_enable_metal=true`,
`angle_enable_gl=false`, xrOS deployment target **26.0**
(`~/dev/realrtcw-ios/work/angle-PROVENANCE.md:42-114`;
`~/dev/q2repro-ios/scripts/build-angle-{ios,visionos}.sh`). **No macOS
slice exists** — that matters for the spike plan below.
ANGLE-Metal caps at **ES 3.0**, never 3.1 (q2repro
`artifacts/angle-metal-caps.txt`, `DECISIONS.md` D3); PD needs nothing
above 3.0, so this is fine.

### 1.6 The ANGLE perf risk for Phase 6

`~/dev/q2repro-ios/FOVEATION-PERF-CONSULT.md:25-56` is specific and it
lands squarely on PD's endgame. In a CompositorServices stereo path the
swap gate deliberately **skips `eglSwapBuffers`** — which is ANGLE's only
natural backpressure, because `DisplayMtl.mm` creates a plain
`newCommandQueue` with no frames-in-flight cap. Command buffers then pile
up unbounded (growing latency), and when ANGLE's internal ceiling of 64
uncommitted buffers is hit the **main thread blocks inside arbitrary GL
calls** — hitching that reads as a port bug. q2repro's fix was to
transplant a 2-deep fence discipline into the glue by hand (:65-96).
An 80-simulant match with XBLA art is precisely the workload that
exceeds the frame budget and triggers this. Option (b) does not have the
problem: we own the command queue.

## 2. Option (b) — native Metal backend

### 2.1 Interface delta vs. sm64coopdx (the file we would seed from)

`~/dev/sm64coopdx-ios/vendor/sm64coopdx/src/pc/gfx/gfx_rendering_api.h:11-36`
is a **24-entry** struct; PD's is **44**. Against PD's list:

- **13 identical** signatures: `get_name`, `unload_shader`,
  `load_shader`, `shader_get_info`, `new_texture`, `draw_triangles`,
  `init`, `on_resize`, `start_frame`, `end_frame`, `finish_render`,
  `set_viewport`, `set_scissor`.
- **8 changed**: `get_clip_parameters` (sm64: `z_is_from_0_to_1`, and PD
  additionally returns `invert_y` — `gfx_opengl.cpp:80-82`, consumed at
  `gfx_pc.cpp:2211`); `create_and_load_new_shader`/`lookup_shader`
  (**PD keys on `uint64_t shader_id0, uint32_t shader_id1`**, sm64 on a
  `struct ColorCombiner*`); `select_texture` (+`linear_filter`);
  `upload_texture` (+`gen_mipmaps`, u32 dims); `set_sampler_parameters`
  (+`mipmaps`); `set_depth_mode` (folds sm64's three depth calls and adds
  `depth_source_prim` + `zmode`); `set_use_alpha` (+`modulate`).
- **23 absent from sm64 entirely**: `get_max_texture_size`,
  `clear_shaders`, `set_depth_range`, the nine framebuffer entries
  (`create_framebuffer`, `update_framebuffer_parameters`,
  `start_draw_to_framebuffer`, `copy_framebuffer`, `clear_framebuffer`,
  `resolve_msaa_color_buffer`, `get_framebuffer_texture_id`,
  `select_texture_fb`, plus `get_max_msaa_level`), `delete_texture`,
  `set_texture_filter`, `get_texture_filter`, `set_mipmap_filter`,
  `set_anisotropy_level`, `get_max_anisotropy_level`,
  `read_screen_pixels`, and the four capture entries.
- sm64 has one entry PD lacks (`shutdown`).

**Delta count: 31 of 44 entries are new or changed.** sm64's 1736-line
`app/gfx/gfx_metal.mm` gives us the *mechanics* for maybe 40% of the
surface, not the surface itself.

### 2.2 What `gfx_pc.cpp` actually does with the new entries

- `create_framebuffer` ×2 at init (`gfx_pc.cpp:3830-3831`) plus one per
  game-side framebuffer (`:4168` — `chr.c`'s shield textures, held across
  a renderer re-init, which is why `select_texture_fb` bounds-checks at
  `gfx_opengl.cpp:1528`).
- `update_framebuffer_parameters`, seven call sites (`:3826`, `:3968`,
  `:3989`, `:3995`, `:4000`, `:4027`, `:4183`). `render_target` and
  `can_extract_depth` are passed but **never read** by the GL backend —
  PD's API has **no `get_pixel_depth`**, so depth is never read back and
  a Metal backend can ignore both. Real work: resize a color texture, a
  depth/stencil texture, and an MSAA color+depth pair.
- `start_draw_to_framebuffer(fb, noise_scale)` (`:4031`, `:4043`,
  `:4197`, `:4223`) — `noise_scale` becomes `1/noise_scale` in a uniform
  (`gfx_opengl.cpp:1471-1473`) feeding the dither hash.
- `resolve_msaa_color_buffer` + `get_framebuffer_texture_id`
  (`:4051-4057`) — the resolved id is published as the global
  `gfxFramebuffer` (`gfx_pc.h:18`) and fed back in as a texture.
- `copy_framebuffer(dst, src, left, top, flip_y, use_back)` (`:4219`) —
  scaled-or-unscaled blit with an optional vertical flip; Metal needs a
  blit encoder (unscaled) or a one-triangle draw (scaled/flipped).
- `clear_framebuffer`, `select_texture_fb`, `delete_texture`,
  `set_texture_filter`/`get_texture_filter` (FILTER_THREE_POINT changes
  the emitted shader, so a change must invalidate the shader cache),
  `set_mipmap_filter`, aniso ×2, `get_max_msaa_level` (`:3838`, `:3977`),
  `read_screen_pixels` (`video.c:260`), capture ×4 (`video.c:276`; may be
  left NULL — `gfx_pc.cpp:4084-4106` null-checks every one).

### 2.3 The second donor: libultraship's Metal backend

`~/dev/harbourmasters/libultraship`:
`src/fast/backends/gfx_metal.cpp` 1296 lines +
`include/fast/backends/gfx_metal.h` 245 +
`src/fast/backends/gfx_metal_shader.cpp` 285 +
`src/fast/shaders/metal/default.shader.metal` 304 ≈ **2150 lines**.

It implements, with real code we can read: framebuffer create/update with
MSAA via `StoreActionStoreAndMultisampleResolve` (`gfx_metal.cpp:800-816`),
`ClearFramebuffer` by closing and reopening the encoder with
`LoadActionClear` (`:915-966`), `CopyFramebuffer` as a blit encoder
(`:1106-1177`), `ResolveMSAAColorBuffer` (`:968-1019`),
`GetFramebufferTextureId` returning the raw `MTL::Texture*` (`:1097-1099`),
`SelectTextureFb` (`:1101-1104`), `StartDrawToFramebuffer` with
`noiseScale` (`:881-913`), **three-point filtering entirely in MSL**
(`default.shader.metal:140-156`, per-slot via
`drawUniforms.textureFiltering[i]`) with a shader-cache flush on filter
change (`:1264-1267`), and runtime MSL compilation by
`newLibrary(NS::String…)` (`:227-228`) with a pipeline-state variant per
sample count (`:272-290`).

But it is **not** the same API generation as PD's: LUS's `shader_id1` is
`uint64_t` (PD's is `uint32_t`); `CopyFramebuffer` takes ten explicit
rect ints instead of PD's `left/top/flip_y/use_back`; it adds
`GetPixelDepth`, `ReadFramebufferToCPU`, `SetSrgbMode`,
`ClearDepthRegion`, `GetTextureById`, `SetCurrentPrimDepth`; and it has
**no** anisotropy, **no** mipmap filter, **no** `get_max_msaa_level`, and
**no** capture entries at all (every texture is `setMipmapLevelCount(1)`,
`gfx_metal.cpp:353/725/779/838`). Its shader generator is a *prism*
template processor over an `.o2r` resource, not a C string builder —
porting it wholesale drags in a dependency we do not want.
Its layer comes from `SDL_RenderGetMetalLayer` (`:73-93`), i.e. it needs
an SDL_Renderer.

**Which donor is closer:** LUS is closer *structurally* — roughly 30 of
PD's 44 entries have a direct LUS analogue, including every hard one
(framebuffers, MSAA, resolve, three-point, noise_scale, u64 shader ids,
clip parameters). sm64coopdx is closer *operationally* — plain C struct
of function pointers, SDL2, an iOS/visionOS app shell that already works,
`SDL_Metal_CreateView`/`SDL_Metal_GetLayer` rather than an SDL_Renderer
(`app/gfx/gfx_metal.mm:390-395`), a hand-written MSL generator with no
prism, and **a stereo path already shipping**: `stereo_eye_tex[2]`,
`stereo_depth_tex`, `stereo_msaa_tex`, `stereo_msaa_depth`
(`gfx_metal.mm:245-253`, targets built at `:1383-1440`).
Plan: seed the file from sm64coopdx, transplant LUS's framebuffer/MSAA/
three-point logic entry by entry, write aniso/mipmap/capture ourselves.

**Estimate: 2200–2800 lines of new `app/gfx/gfx_metal_pd.mm`**, of which
~900 are near-mechanical from sm64 (init, buffers, pipeline state,
texture upload, sampler state, draw), ~700 adapted from LUS
(framebuffers, MSAA, copy, resolve), ~500 the MSL generator rewritten to
mirror `gfx_opengl.cpp:240-731` construct for construct, ~300 new
(aniso, mipmaps, `read_screen_pixels`, Vivid Colours). Risk is
concentrated in the MSL generator: any combiner permutation that
mistranslates is a *wrong picture*, not a compile error, and PD's
generator has fog-from-z/w, stretched-edge clamp, text outline and
2-cycle wrap that sm64's does not.

## 3. Common ground: drawable, visionOS, Vivid Colours, XBLA

**Drawable.** Both options take the same first step:
`SDL_Metal_CreateView(window)` → `SDL_Metal_GetLayer` → `CAMetalLayer*`.
(a) hands that layer to `eglCreateWindowSurface`; (b) calls
`nextDrawable` on it directly. Note `gfx_sdl2.cpp:127` sets
`SDL_WINDOW_OPENGL` — under ANGLE-via-EGL that flag must go (SDL must
not try to make its own EAGL context), and under Metal likewise. Either
way `gfx_sdl2.cpp` needs an overlay patch for an iOS window row.

**visionOS 2D.** Identical either way — one flat window, one layer.
(a) needs the xrOS ANGLE slices, which exist on disk (§1.5). (b) needs
nothing extra.

**Phase 6 stereo.** (b) wins cleanly: both eyes are ordinary off-screen
`MTLTexture` render targets, which is exactly what `CompositorServices`
wants and exactly what sm64coopdx already does (`gfx_metal.mm:245-253`,
`:1383-1440`), and PD's existing `create_framebuffer` /
`start_draw_to_framebuffer` / `get_framebuffer_texture_id` triple is
already the right shape to express it. (a) must get GL render targets
into `cp_drawable` textures — an IOSurface/EGLImage wrap or a copy per
eye per frame — *and* carries the unbounded-command-buffer hazard of
§1.6, which is the single largest known risk in this document.

**Vivid Colours / Black Level.** Written today as a desktop-GL-3.0-only
pass (`gfx_opengl.cpp:1125-1347`, refused on `gl_es` at `:1210`). Both
options must reimplement it (~60 lines ESSL 300, or one MSL pass). It is
a Phase 2 checklist item, so neither option gets to skip it.

**XBLA textures.** No special demand on the backend. Records cap at
`XBLATEX_MAXDIM 4096` (`xblatex.c:35`); `gfx_pc.cpp:3851` caps the
upload staging buffer at `min(8192, get_max_texture_size())`. ANGLE-Metal
and Metal both report ≥8192 (Apple GPU family 4+: 16384), so the cap
binds first and nothing exceeds it. Enhance Textures multiplies the ROM's
own texels only (`gfx_pc.cpp:964-995` comment: "the XBLA release's
picture only where it is still the ROM's size"), so 8× does not turn a
4096 record into 32768. Format is always RGBA8 (`gfx_opengl.cpp:770`);
mip chains come from `glGenerateMipmap` (`:771-773`) — under Metal that
becomes a blit encoder `generateMipmapsForTexture`, which LUS does not
have (single-mip everywhere) and sm64 does not either, so it is new code
in both donors. Residency math belongs in `docs/memory-math.md` (0.6),
not here.

## 4. Recommendation

**Spike (a), ANGLE-Metal, as the charter plans — but budget the ~70-line
patch set in §1.4 up front, and treat Vivid Colours as a deliverable of
the spike, not an afterthought.** Reasons, in order of weight:

1. The ES 3.00 legality audit came back **clean**. The generated GLSL
   needs no restructuring — two precision lines, and the version/in/out/
   `texture()` selection is already correct. That was the load-bearing
   unknown and it resolved in ANGLE's favour.
2. The prebuilt ANGLE slices for iOS *and visionOS* are already on disk
   with provenance; the family has two shipping ports on this substrate.
3. (b) is 2200–2800 lines of new code whose failure mode is a silently
   wrong picture across hundreds of combiner permutations, against an
   oracle we do not yet have running. That is a Phase 3 project, not a
   Phase 0 one.

**Keep (b) as the declared Phase 3/6 lever**, not a fallback of last
resort, because §1.6 says the ANGLE stereo path will need hand-built
backpressure and §2.3 says a Metal backend makes Phase 6 trivial. Write
the backend seam in `video.c` as a build-time switch on day one
(it already is one — `video.c:79-80`) and never let a second copy of
`gfx_pc.cpp` come into existence.

Uncertainty I am not hiding: I have not compiled a single shader through
ANGLE's translator. The §1.2 verdict is a spec reading, and ESSL's
reserved-word and implicit-conversion rules are exactly where a spec
reading goes wrong. That is what step 1 of the spike is for.

## 5. Spike plan (do not start — this is the brief for the next round)

**Step 1 — shader legality, on the oracle, no ANGLE runtime needed (~2 h).**
Add a throwaway `--dump-shaders` overlay to `gfx_opengl.cpp` (~20 lines:
write `vs_buf`/`fs_buf` to disk at `:613`) and force
`gl_glsl_version_str = "300 es"` under a flag. Run the clang oracle
through the title screen, one Combat Simulator match and one mission with
XBLA art on and off, with three-point/blur/aniso toggled — that
enumerates the combiner permutations the game actually uses. Feed every
dumped pair through ANGLE's `angle_shader_translator` (or
`glslangValidator -S frag --client opengl` in ESSL-300 mode).
**Proves:** every permutation PD generates is legal ESSL 3.00, or names
the exact ones that are not. Cost: cheap, no ANGLE build, no device.

**Step 2 — runtime to the title screen (~1 session).** There is **no
macOS ANGLE slice on disk** and building one is hours, so the cheapest
honest runtime target is the **iOS simulator on lane 3 (iPhone 17e, iOS
27.0)** using the existing `ios-arm64-simulator` slice. Write
`app/gfx/gfx_egl.mm` (~150 lines, ported from
`realrtcw-ios/app/Sources/ios_egl.m` to SDL2), apply patches P1–P4, drop
`SDL_WINDOW_OPENGL`, and drive to the title screen with
`--skip-intro --screenshot-frame`.
**Proves:** shaders compile *in situ*, the framebuffer/MSAA/resolve path
is complete under ANGLE-Metal, the screenshot instrument survives P4, and
the whole thing presents. Artifact: a content screenshot of the title
screen, diffed against the oracle's.
**If the user prefers the oracle strictly**, the alternative is
`build-angle-ios.sh` re-pointed at `target_os="mac"` first — add 2–4 h
